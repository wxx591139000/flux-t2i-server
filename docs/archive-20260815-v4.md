## 本次归档变更摘要

**v1.4 — 队列服务器恢复自动重试（根本性修复）**

用户核心诉求："**你要从根本上让流程能自动走，不要手动介入**"。

旧版致命缺陷：FLUX 服务器 down 时，队列任务**重试 3 次就标 failed**，服务器恢复后**没有自动恢复机制**，任务永远失败，必须手动重新提交。

修复（对齐转录项目 orchestrator `_recover_failed_tasks` 机制）：

| 时机 | 旧行为 | 新行为 |
|---|---|---|
| 服务器 down | 立即重排，几秒打满 3 次 retry → failed | 任务进 `waiting` 池（状态 `waiting`），**不失败、不立即重排** |
| 服务器恢复（30s健康监控检测到） | 无恢复机制，任务永远失败 | `_recover_waiting_tasks()` **自动重新入队**继续生成 |
| 恢复次数超限 | — | 每任务最多恢复 3 次，超限标 failed + `[RECOVER_SKIP]`（防毒瘤） |
| 服务重启 | waiting 任务丢失 | `_recover_stale_waiting()` 启动时恢复 DB 遗留 waiting 任务 |

**改动文件**：
- `manager/flux_queue.py`：`_process` 服务器 down 改进 waiting 池；`_health_loop` 加恢复分支；新增 `_recover_waiting_tasks` / `_recover_stale_waiting`；`__init__` 加 `_waiting` 集合
- `manager/flux_db.py`：新增 `jobs_waiting()` 查询
- `manager/flux_web_service.py`：任务状态新增「等待服务恢复」；修 `sqlite3.Row` 无 `.get()` 的 bug（改用索引访问）
- `docs/`：CHANGELOG / PITFALLS / PROGRESS 更新 v1.4

**验证**：
- 单元测试全过：down→waiting 不失败 → up→自动入队 → 生成完成；重试上限生效
- 真实任务跑通：之前 failed 的"女人和狗打架"任务重新提交后成功生成
