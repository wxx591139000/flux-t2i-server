### 2.2 我们手上的是"蒸馏版"，不是 Base 版

这两个版本**完全不同**，容易混淆（我们从未在文档里写清，是本次补上的）：

| | 蒸馏版（**我们在用**） | Base 版 |
|---|---|---|
| 权重文件 | `flux-2-klein-4b.safetensors` | `flux-2-klein-base-4b.safetensors` |
| 推理步数 | **4 步固定** | 50 步（可调） |
| guidance | **1.0 固定** | 4.0（可调） |
| 速度 | 亚秒 | 慢 10–50 倍 |
| 输出多样性 | 较低 | 高 |
| 用途 | 生产、实时 | 微调、研究、最大多样性 |
| 授权 | Apache 2.0 | Apache 2.0 |

**我们装的是哪个**：源码里 `num_inference_steps=4, guidance_scale=1.0` 写死在
`StubPipeline` 签名与 `MODEL_PROFILES` 里，且实测 `du` 出的 15 GB 与蒸馏版一致。
**未在真机核对 safetensors 文件名** —— 这是本报告唯一没能验证的点，
GPU 机开机后可用一条命令确认：


### 2.3 已知短板（来自官方与社区，非我们实测）

| 短板 | 严重度 | 对我们（电商商品图）的影响 |
|---|---|---|
| **文字渲染明显弱于大模型** | 中 | 若图里要出现品牌字/标价 → 需换 9B 或 FLUX.2 [flex]（专门做文字） |
| **照片真实感与细节弱于 9B / 32B** | 中 | 高端商品主图（皮革纹理、金属反光）会显得"平"，需评估 |

| 可能放大训练数据偏见 | 低 | 商品图场景基本无影响 |

## 三、升级候选（同许可 / 可商用）

| 模型 | 参数 | 显存 | 步数 | 许可 | 商用 | 获得方式 |
|---|---|---|---|---|---|---|
| **klein 4B**（当前） | 4B | ~13 GB | 4 | **Apache 2.0** | ✅ | 本地已装 |
| **klein 4B Base** | 4B | ~13 GB | 50 | **Apache 2.0** | ✅ | HF 免费下载 |
| klein 9B | 9B | ~24 GB | 4 | FLUX NCL（**非商用**） | ❌ | HF 下载 |
| klein 9B Base | 9B | ~24 GB | 50 | FLUX NCL（**非商用**） | ❌ | HF 下载 |
| FLUX.2 dev | 32B | 80 GB（优化后 40 GB+） | 50 | FLUX NCL（**非商用**） | ❌ | HF 下载 |
| FLUX.2 [flex] | — | API | — | 商用 API | ✅ 付费 | BFL API |
| FLUX.1-dev（旧机器 flux1） | 12B | 32G（offload=model） | 25 | **非商用** | ❌ | 本地有 |

**⚠️ 关键约束（这条决定了很多事）**：
**9B 及以上全部是 FLUX Non-Commercial License —— 不能商用。**
我们做的是对外经营的电商商品图服务，所以：

- **能合法商用的本地模型，就只有 4B 系列（Apache 2.0）。**
- 想提升质量又必须商用 → 只有三条路：
  1. 换 **4B Base**（50 步、多样性高，但慢 10–50 倍，且不解决"细节弱"的根本问题）
  2. 用 **BFL 官方 API**（flex/pro，付费，质量最高，但要按张计费）
  3. 用**其他厂商的商用许可模型**（如阿里通义万相、即梦等，需单独评估）

> 这条比"选哪个模型"更重要：**如果商用是硬需求，9B/dev 整个类别就被排除了**，
> 不要在它们身上花时间做质量对比。

## 四、质量瓶颈诊断：先修参数，再谈换模型

**这是本报告最有价值的部分。** 我们花了一天时间实测"步数对质量的影响"，
结论是 —— **在当前部署下，调步数几乎不产生有效计算**，原因是采样参数配置有误。

### 4.1 实测数据（2026-09-20，同 prompt / 同 seed / 同尺寸）

| 步数 | 耗时 | 备注 |
|---|---|---|
| 8 步 | 14 s | 图生图任务 |
| 15 步 | 16 s | 队列空闲时 |
| 15 步 | 148 / 166 s | 队列拥挤时（同一配置） |
| 35 步 | 164 / 343 s | 队列拥挤时 |

**读法**：同样 15 步，耗时从 16 s 到 166 s —— 差异**全部来自队列拥挤**，与步数无关。
这说明在蒸馏模型上，`num_inference_steps` 从 15 改到 35 **没有带来可观测的计算增长**，
因为模型在第 4 步就已完成去噪，其后的步数只是在已收敛的轨迹上空转。

### 4.2 根因（已在本次修复）

`DEFAULT_STEPS = 25` / `DEFAULT_GUIDANCE = 3.5` 是 **FLUX.1-dev 时代**的默认值，
换到 klein 后**从未按模型校正**：

- **guidance 恒用 3.5，应为 1.0** —— 蒸馏版把 CFG 烘进了权重，推理时必须给 1.0。
  给 3.5 属于超范围外推。**这是从部署第一天起就在静默发生的质量损失。**
- **默认 25 步，应为 4** —— 多出的步数近乎空转。

修复方式：新增 `MODEL_PROFILES`，采样参数画像**跟着模型走**
（klein → 4 步/1.0/上限 8；dev → 25 步/3.5/上限 100），并暴露到 `/health`。
回归门 `tests/test_model_profile.py`（19 项）钉住，含变异测试。

### 4.3 所以正确的行动顺序是

1. **先让新参数在真机生效**（GPU 机开机 → 重启常驻 → 跑一次验收）
2. **再看质量是否已经够用** —— 很可能够了，因为之前一直跑在错误的 guidance 上
3. **若仍不够，再考虑换模型** —— 且优先考虑 4B Base（仍可商用）

**不要跳过 1、2 直接换模型**，那样会把"参数错误"误判成"模型能力不足"，
然后花钱买一个本来就够用的东西。

## 五、评估"值不值得换"的判断框架

问三个问题，按顺序：

**Q1：现在的图，客户抱怨什么？**
- 抱怨"慢" → **别换**，4B 已是速度最优；检查链路（实测瓶颈在 AutoDL 下行 ~3.6 KB/s）
- 抱怨"细节不够 / 不够真实" → 先做第 4.3 节的参数修复，再评估
- 抱怨"图里有字但字是乱的" → **确实需要换**（klein 4B 文字渲染是公认短板）
  → 候选：FLUX.2 [flex]（专做文字，付费 API）或别的商用文字模型

**Q2：商用是硬需求吗？**
- 是 → 9B / dev **全部出局**（非商用许可），只能在 4B 系列 + 付费 API + 其他厂商里选
- 否（内部测试/研究） → 可以试 klein 9B（~24 GB，需换 32G 以上卡）

**Q3：换模型的成本能接受吗？**
| 方案 | 成本 | 风险 |
|---|---|---|
| 4B → 4B Base | 免费（HF 下载 15 GB），**慢 10–50 倍** | 生产环境基本不可用（除非离线批量） |
| 4B → klein 9B | 免费下载 + 需 ~24 GB 显存（现卡 32 GB 够） | **非商用**，商用场景违法 |
| 用 BFL 官方 API | 按张计费（官方标价约 $0.014 + $0.001/MP） | 依赖外部服务、数据出境 |
| 其他厂商商用模型 | 各家不同 | 需重新做链路适配 |

## 七、给下一个接手的人的提醒

1. **模型不是"越大越好"，也不是"许可随便选"** —— 9B/32B 全是非商用许可，
   我们做对外服务，这条是硬约束。
2. **采样参数是模型属性，不是全局常量** —— 换模型必须同时换参数画像，
   否则会重演"klein 跑了 25 步 + guidance 3.5"这个静默劣化。
   `MODEL_PROFILES` 是唯一入口，加模型就往那里加一条。
3. **调参之前先确认参数真的生效** —— 我们曾花大量时间在"15 步 vs 35 步"上，
   而真实情况是两者在蒸馏模型上都不产生有效计算。
   `/health` 的 `profile` 字段就是为了让这件事可观察。
4. **官方文档 vs 实测**：本报告的步数/guidance/许可来自 **BFL 官方一手来源**
   （blackforestlabs.ai 博客 + docs.bfl.ai + HF 模型卡）；
   耗时与显存是**本机实测**。两者都已标注来源，不要混用。
