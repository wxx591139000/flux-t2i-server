## 本次归档变更摘要

**主题一：任务彻底删除（墓碑模式）** · 上游 `911198d` + 站点 `1cdcee0`

用户可单独点击彻底删除任务记录与图片。此前上游**没有删除端点**，本轮新增。
用户明确的三条口径：**① 不退配额 ② 上游与站点两边都做 ③ 任何状态都能删**。

### 为什么打墓碑（`deleted_at`）而不是 `DELETE` 行

worker 是异步的，用户点删除时任务**可能正跑在 GPU 上**。直接删行会造成三个后果：

1. worker 完成后 `UPDATE` 落到不存在的行
2. 完成后写出的 PNG 变成**孤儿文件** —— 永远清不掉
3. 队列 / 去重键竞态无人兜

墓碑让 worker 跑完后能**自查并清理**，三个问题一并解决。

### 配额口径（关键，最容易被后来的重构"顺手优化"掉）

`usage` 在**入队时 +1**（`manager/flux_queue.py:210`），是**消耗计数**而非"当前持有数"。
所以删除**绝不退配额** —— 否则用户可"删了重传"无限刷，套餐形同虚设。
（已失败任务本来就走 `refund_job_once` 退过款，与此无关。）

### 改动清单

| 文件 | 改动 |
|---|---|
| `manager/flux_db.py` | jobs 加 `deleted_at`（幂等迁移）；新增 `job_get_alive` / `jobs_abandoned` / `job_mark_deleted` / `job_hard_delete`；`job_by_user` / `jobs_queued` / `job_count_queued` / `jobs_waiting` 全部加 `AND deleted_at IS NULL`；`list_jobs` 保持含墓碑（管理口径） |
| `manager/flux_web_service.py` | 新增 `POST /api/delete`；`_api_download` 加墓碑检查（→404）；`_purge_job_image` 只删单文件 + `web_out/<job_id>/`（**绝不 rm -rf**）；任务列表加"操作"列（首页与任务中心两处） |
| `manager/flux_queue.py` | 新增 `drop_job`；`_process` 开头墓碑短路 + 生成后二次自查产物并收尾 |
| `image-gen-site` | `deleteJob()` provider；`app/api/jobs/[jobId]/route.ts`；每张卡加「彻底删除」 |

**越权防护钉在 SQL 层**：`job_mark_deleted` 的 `WHERE job_id=? AND user_id=?`，
不依赖上层记得校验。

**站点必须转发（不能让前端直连上游）**：token 由 **httpOnly cookie 派生**，前端拿不到。
若为图方便把 token 暴露给 JS，等于把归属边界交给页面，一个 XSS 就能删任意访客的任务。

### 顺带消除的生产风险

`sqlite3.Row` 取**不存在的列**抛 `IndexError`（不是返回 None），而 `_process` 跑在
worker 线程 —— 任何未捕获异常都会**打死 worker**（此后所有任务永远卡 queued、网站一直转圈）。
老库没跑到 `ALTER TABLE` 迁移时 `fresh['deleted_at']` 就会炸。已加 `_row_value()` 防御式读取。

**主题二：看门狗作为子路径纳管**

### 为什么"纳管"这件事本身是必要的

2026-09-21 修完删除端点后逐条手动跑门，跑完就宣布"全绿" ——
**但当时并没有把所有子路径都跑一遍**，看门狗那组是后来才想起来补跑的。

手动列举的清单一定会漏；**漏掉的那组不报错，只是静默地不被执行**，
而这跟"它通过了"在输出上长得一模一样。所以本轮做了两件事：

1. **看门狗新增第 [8] 组门**：把"反向覆盖"这个最反直觉的性质钉住（见下）
2. **新增 `tests/run_all.py`**：**扫 `tests/test_*.py` 全跑**，而不是维护一份"要跑哪些"的清单
   （那又是一份会漂移的副本）。新加门 = 往 `tests/` 放个文件，自动纳入；
   想排除必须显式写进 `SKIP` 并说明理由。

### 看门狗最反直觉的性质：反向覆盖

看门狗每 60s 比对「GPU 机文件 vs VPS `/opt/flux-watchdog/mirror/`」，
**不一致就用 mirror 覆盖远端**。这把"本地 → 远端"的直觉整个反过来了。

实锤症状：改了 `server/` 下的常驻文件后 scp 到 GPU 机，
**上传后立刻校验 PASS，几十秒后 md5 变回旧值**（mtime 却是新的，很像"写入未落盘"）。

**正确顺序**：改了 `server/` 下的常驻文件 → 第一动作是 `deploy_vps.py`（更新 mirror），
**不是 scp 到 GPU 机**。mirror 更新后 GPU 机 ≤60s 自动同步，可以完全不手动上传。

排查口诀：**先看 mirror 的 md5，别只盯目标机**：
```bash
ssh vps-aliyun "md5sum /opt/flux-watchdog/mirror/*"
```

### 本轮补上的真实缺陷

`deploy_vps.py` 上传 mirror **没有任何校验** —— 一次静默截断的上传会让坏文件
成为"权威副本"，然后被推给所有机器。已新增 **落盘 md5 逐文件比对**，
任一不符即**中止部署**（宁可不部署，也不把坏副本推成权威版本）。

## 本轮新增踩坑（全文见 `docs/PITFALLS.md`）

1. **看门狗反向覆盖** —— 手动上传会被 ≤60s 打回，症状是"md5 回退但 mtime 是新的"
2. **`sqlite3.Row` 取不存在列抛 `IndexError`** —— 在 worker 线程 = 打死 worker，全队列永久卡死
3. **"改了代码没生效"真因是进程陈旧** —— 症状是 404 + 非 JSON，会把排查引向协议层
4. **替身必须与真身同口径** —— stub 缺 `/api/delete` 会让离线全绿而线上错
5. **手动列举的测试清单必然漏** —— 改"扫目录"而不是"写清单"
