# 生图延迟根因分析（2026-09-21）

> 用户报：「点提交后要等 **1 分钟**网页才出现任务状态卡片，再等 **1 分多钟** GPU 才有反应」
> 提问：英文提示词不需要翻译，为什么还这么慢？
>
> **结论先行**：延迟与提示词翻译**完全无关**（英文根本没进翻译层）。真正的耗时在
> **① 单 worker 串行导致 3 连任务排队** + **② 每张图 10~16 秒的 SSH 探活/协调开销**
> （推理本身只要 2~3 秒，占比不到 5%）。

---

## 一、先排除「翻译」这个怀疑对象

用户的直觉是「英文直传应该更快」，这个怀疑可以**直接证伪**：

- `flux_queue.py:184` `original_prompt = prompt if has_chinese(prompt) else None`
- 只有含中文才走 `translate_to_flux_prompt()`
- 查库确认：`e7c08585ed394d7b` 等任务的 `original_prompt` 有值（那批是中文任务），
  而 `5c160cd3082f40aa` 是纯英文的 `/api/edit`
- **实测提交端点耗时**（直连 9620，绕过代理）：

  ```
  GET  /health           : 0.01s
  POST /api/submit  #1   : 0.04s -> {"job_id": "860d4d4bacdf4a03", "status": "queued"}
  POST /api/submit  #2   : 0.04s -> {"job_id": "9d58c508a4574a90", "status": "queued"}
  POST /api/submit  #3   : 0.03s -> {"job_id": "2c70eec269b64347", "status": "queued"}
  ```

  **提交是毫秒级返回的**。翻译层即使被调用也是网络往返级（百毫秒），解释不了 1 分钟。

→ 所以「慢」不在提交这一段，也不在翻译。

## 二、真正的耗时：逐阶段实测分解（用户报的那批任务）

用户的 3 连任务 `e7c08585ed394d7b` / `b8ccdb8dfdc14b72` / `4783274739d5417b`
（seed 732551026，720×1280）。从 `manager/flux_manager.log` 取毫秒级时间戳：

### 第 1 张

| 时刻 | 事件 | 距提交 | 花在哪 |
|---|---|---|---|
| 11:50:06 | 用户点提交（POST /api/submit） | — | 提交本身 0.04s |
| 11:50:14.768 | `🟢 选中 flux6` | **+8.8s** | **选机：SSH 探活所有候选机** |
| 11:50:22.349 | `🎬 提交给 GPU` | **+7.6s** | **ensure_resident + POST /generate** |
| 11:51:11.638 | `✅ 完成（推理 2.66s）` | +49.3s | 轮询 + 拉图（AutoDL 下行 ~3.6KB/s） |

**从点提交到 GPU 真正开始算 = 16.4 秒。而推理只要 2.66 秒。**

### 3 连是串行的（单 worker）

```
任务#1: 11:50:22 提交 → 11:51:11 完成  (49.2s)
任务#2: 11:51:25 提交 → 11:52:04 完成  (39.8s)
任务#3: 11:52:11 提交 → 11:52:44 完成  (33.0s)
                                        ─────────
                     第 3 张完成时距点提交 = 158 秒
```

`flux_queue.py:357-400`：**`_run_worker` 是单线程串行**（设计如此，注释写着「单 worker 串行」）。
3 张图 = 3 次完整的「选机 + 拉起 + 提交 + 轮询 + 拉图」循环，每次都付一遍 SSH 开销。

## 三、耗时都花在哪：三个主要浪费点

### 浪费点 1：选机要 SSH 探活所有候选机（10.3s）

`flux_resident_client.find_available_server()` → `probe_all()` → **并行探所有 enabled 机器**。

实测（`probe_all(force=True)`，3 台候选）：

```
probe_full #1: 6.47s   reachable=True  gpu_ok=True  model_ok=True
probe_full #2: 4.35s
probe_full #3: 3.50s
find_available_server 冷启动: 10.28s  → flux6
find_available_server 命中缓存: 0.00s
```

**问题**：`manager/servers.json` 里 **flux1 和 flux5 都是 `enabled: true`，但两台都不可达**
（已实测确认）。探活是并行的，所以总耗时 ≈ 1 个 `ConnectTimeout(8s)` —— 每次冷缓存都要等
那 8 秒超时。**两台死机器拖累了唯一活着的 flux6。**

- TTL 缓存 20s（`FLUX_PROBE_TTL`），跨任务基本能命中 → 所以是**每 20 秒付一次 8-10 秒**
- 3 连任务的总时长里，选机大约吃掉 3×8~10s ≈ **25~30 秒**

### 浪费点 2：`ensure_resident` 每次都重新确认（7.6s）

日志显示**每次都是「常驻在跑·模型已加载，零冷启动」**，本来应该秒回。
但从 `选中` 到 `提交给 GPU` 稳定花 **7~15 秒**：

```
11:44:00.595  - 11:43:50.164 = 10.4s
11:45:02.995  - 11:44:53.380 =  9.6s
11:45:49.495  - 11:45:38.067 = 11.4s
11:50:22.349  - 11:50:14.768 =  7.6s
11:53:43.179  - 11:53:28.376 = 14.8s
```

这段包含：`ensure_resident` 内部的 `probe` → `generate_via_resident` 开头的
`GET /health` → `POST /generate`。**每一次都是一次独立的 SSH 往返**，
而 `_ssh()` 给 ssh 加的 `SSH_ROUNDTRIP_OVERHEAD = 20s` 只是超时预算，
实际单次往返 1~3s（AutoDL 中转链路），叠加次数就上来了。

### 浪费点 3：拉图占了大头（每张 30~50s 的端到端 vs 2.6s 推理）

推理 2.3~3.4 秒，但端到端 **33~74 秒** —— 差距几乎全在**轮询 + 拉图**：

- `generate_via_resident` 轮询：起始 1.5s、×1.5 递增、上限 6s
  （每次轮询 = 一次 SSH + curl 往返）
- `fetch_png`：AutoDL 下行实测 **~3.6 KB/s**，920KB 的图要 **200s+**
  （代码里最大超时已经开到 300s，注释写着「783KB 的 PNG 要 200s+」）

→ **这是当前最大的单项成本**，且与 GPU、与翻译都无关，纯粹是网络中转带宽。

## 四、附带发现：站点侧 `steps` 没传

查库：这批任务 `steps` 全是 `NULL`。

- 站点 `app/api/generate/route.ts:40-43`：`steps` 只在 `>0` 时才传
- `app/create/page.tsx` 的 `QUALITY_PRESETS` 里 standard(0) 档位**故意不传**，走上游默认
- 实测 GPU 侧 `profile = {default_steps: 4, max_steps: 8, guidance: 1.0}`
  → **没传 steps 是对的**，上游 klein 蒸馏版固定 4 步，本来就不该传 25

**但 `/health`（9620）仍然没有 `profile` 字段**，只有直查 GPU 才看得到。
→ 这是一个可观测性缺口（见待办）。

## 五、按收益排序的修复建议

| # | 措施 | 预计收益 | 风险 |
|---|---|---|---|
| 1 | **把 flux1 / flux5 的 `enabled` 改 `false`** | 选机 8~10s → ~1s | 无（两台确实不可用） |
| 2 | **`probe_all` 加「首选机优先」** 或按最近成功机排序，只探 1 台 | 选机降到 1 次往返 | 低 |
| 3 | **拉图改走 HTTP 直传**（若 AutoDL 能开端口），或压缩图片后再传 | 省 30~180s/张 | 中（需换链路） |
| 4 | **`ensure_resident` 结果复用**（同批任务共享一次探活） | 省 5~10s/张 | 低 |
| 5 | **3 连改为并行提交**（worker 数量 > 1，或同一台机内批处理） | 3 张总时长 ⬇ 60% | 中（GPU 串行是物理限制，只能省协调开销） |
| 6 | 9620 `/health` 透传 `profile` | 可观测性 | 无 |

## 六、一句话回答用户

> **慢的原因不是翻译**（英文直传，提交只花 0.04 秒）。
> 是 **① 3 张图被单 worker 串行排队** + **② 每张图光「选机 + 拉起 + 提交」就要 8~16 秒的
> SSH 协调开销**（其中约 8 秒纯粹在等两台已停机的 flux1/flux5 超时）+
> **③ 拉图受 AutoDL 下行 3.6KB/s 拖累**。
> GPU 真正算图只要 **2.6 秒**，占总时长不到 5%。
