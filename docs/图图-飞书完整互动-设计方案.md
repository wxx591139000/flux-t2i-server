## 1. 目标与不做什么

### 1.1 目标（"和小白一样的效果"，主题换成生图）

1. 单聊、群聊都能用；群里 @图图 即可
2. 不只是一句话直出：能**问参数**（比例 / 张数 / 模型 / 是否图生图）
3. 有**任务生命周期反馈**：排队 → 生成中 → 完成 / 失败 / 等待，且**不刷屏**
4. 支持**图生图**（发图 + 一句话改图）
5. **额度与身份**打通（激活码 / owner 无限量）
6. **幂等、可恢复**：事件重放不重复出图；重启不丢在途任务
7. 结果是**图片消息**（多张就多张），必要时可打包成文件回传

### 1.2 不做（明确划界，避免范围蔓延）

- 不重写发送层：在 `feishu_notify.py` 上扩展，**不新建第二套飞书客户端**
- 不引入飞书卡片编辑器 / 复杂表单（第一期只做纯文本 + 按钮卡片）
- 不改 A 链的调度与 GPU 侧逻辑（机器人只是**前端**）
- 不做多机器人（图图 = 一个应用，一个 bot 实例）

### 2.2 三个关键架构决策

**决策 1：群聊走「WS 事件」而不是「轮询」。**
小白用「群轮询 + 私聊 WS」的混合方式（`feishu_channel.py:175-199`）。我们**建议统一走 WS**：
- 现有 `FeishuBot` 已经在用 WS，只需**放开 `chat_type` 过滤 + 加 @ 检测**，改动量最小
- 轮询有固有缺点：延迟（poll 间隔）、需要维护群列表、更易触发 429
- 轮询的价值是"补漏"，可作为**可选兜底通道**在 P3 再加（默认不开）
- 前置条件：飞书应用需要开 `im:message.group_at_msg`（仅接收 @机器人）或 `im:message.group_msg` 权限，且机器人被拉进群

**决策 2：状态机 key 用三元组 `(channel, chat_id, sender_id)`，一开始就带上 `chat_id`。**
小白用的是二元组 `(channel, sender_id)`（`orchestrator.py:353`），后来只能靠"额外跨会话校验 + 冷却"打补丁（`:380-383, :470`）。
**我们直接按三元组建模**，把这个补丁变成模型本身的一部分。

**决策 3：所有状态落 DB，不只放内存。**
现有 `self._active` 是纯内存 dict（`feishu_bot.py:41`），所以**重启 9620 后在途任务的结果永远回不来**。
小白有 `_requeue_pending_tasks()`（`orchestrator.py:1204`）。我们照做：
- `jobs` 表已有 `status`，重启后扫描 `queued/generating` 的任务，重建跟踪并继续回传
- 待选状态也要落表（否则重启后用户回复"2"没人接）

## 3. 交互设计（把主题换成生图任务）

### 3.1 单聊主流程

```
用户：一只橘猫坐在窗台上，阳光洒落
图图：┌ 准备出图 ─────────────────┐
      │ 提示词：一只橘猫…（前 40 字） │
      │ 比例：1:1    张数：1         │
      │ 模型：默认（klein）          │
      │ [ 直接出图 ] [ 改参数 ]      │
      └──────────────────────────┘
用户：直接出图  （或点按钮 / 回 "1"）
图图：⏳ 已排队 · 第 2 位 · 前面还有 1 个任务
图图：（同一条消息被编辑，不刷屏）
      🎨 生成中… · 已用 42s · 任务 a1b2c3d4e5f6
图图：[图片]
图图：✨ 完成 · 耗时 63s · 💳 本月 17/200
      [ 再来一张 ] [ 换比例 ] [ 查看我的额度 ]
```

失败与异常：

| 情形 | 回执 |
|---|---|
| 额度用尽 | `❌ 本月配额已用 200/200 张。回复 /quota 查看，或续费激活码。` |
| GPU 不可达 | `🔴 服务器暂不可达，任务已进入等待队列，恢复后自动继续（不会丢）` |
| 生成失败 | `❌ 生成失败：<原因前 200 字>` + `[ 重试 ]` 按钮 |
| 在途过多 | `⏳ 你已有 2 个任务在生成，请等一个完成再来～`（**不静默丢弃**） |

### 3.2 群聊流程

```
群成员A：@图图 一只戴墨镜的柴犬
图图：（只有一条「群看板」消息，之后一直**编辑它**）
      ┌ 群内生成中 ────────────────┐
      │ 发起人：@A                  │
      │ 提示词：一只戴墨镜的柴犬      │
      │ 状态：生成中 · 38s           │
      │ 队列：本群 1 个在跑 / 0 等待  │
      └──────────────────────────┘
图图：@A 你的图好了 👇 + [图片]     ← 结果 @ 发起人，不 @ 全群
```

群聊硬规则：
1. **必须 @图图** 才响应（对齐小白 `feishu_channel.py:218`）
2. **群内待选项按发起人隔离**：A 的"改参数"待选，B 回复"1"**不能消费**（三元组 key 天然保证）
3. **默认只发一条可编辑的看板**，不逐条刷屏
4. **群里每人每天上限**（可配），防止外人滥用
5. 结果图 **@发起人** 发送，不打扰全群

### 3.3 图生图流程（发图 + 一句话）

```
用户：[发送一张商品图]
图图：这张图用来做什么？
      [1] 换背景   [2] 改风格   [3] 局部修改   [4] 仅作参考
用户：2 换风格
图图：好，说说想要什么风格（回复一句话即可）
用户：北欧极简，浅木色桌面
图图：⏳ 已排队（图生图）…   → [改图结果]
```

**必须有的守卫**（照抄小白的教训）：
1. **冷却**：上传图片后的 **N 秒（建议 5s）内**，后续文本**不当作"选择"** —— 防飞书把"图片 + 附言"拆成两条事件时把附言吃掉
2. **非选择意图不消费**：空文本 / 等于文件名 / 以 `/` 开头（命令优先放行）→ **不消费待选状态**
3. **超时**：待选默认 **300s** 过期，过期后回一句"已取消，请重新发图"
4. **状态落 DB**：重启后仍能接住用户的回复

### 3.4 命令面（对齐小白的斜杠命令）

| 命令 | 作用 |
|---|---|
| `/help` | 用法说明（首次对话自动发一次） |
| `/quota` | 我的套餐 / 本月用量 / 剩余 |
| `/size 1:1\|16:9\|9:16\|4:3\|3:4` | 设置默认比例（持久到会话） |
| `/n 1..4` | 设置默认张数 |
| `/model klein\|dev\|qwen` | 选择模型（**按模型能力表提示可用性**，不可用的明确说原因） |
| `/cancel` | 取消待选项 / 取消我排队的任务 |
| `/redo` | 用上一条提示词再出一张 |
| `/bind <激活码>` | 把飞书身份绑定到已有账户（复用 `/api/activate` 语义） |
| `/id` | 显示我的 open_id / 账户（便于排查） |

> **模型可用性提示必须来自一手事实**（`server/flux_resident_server.py:901-935` 的 `MODEL_CAPABILITIES`），
> 不要硬编码"支持什么"。例如 dev 只能文生图、klein 只接受单张参考图、Qwen 才支持多参考图与透明背景。
> 用户选了一个当前 GPU 机不支持的组合时，要在**提交前**明确拒绝并说明原因，而不是等 A 链报错。

## 4. 数据模型（新增三张表）

```sql
-- ① 幂等：飞书会重放事件；文件场景必须双键（小白 PITFALLS #1）
CREATE TABLE IF NOT EXISTS feishu_dedup (
    event_key   TEXT PRIMARY KEY,        -- 'evt:{event_id}' 或 'filekey:{file_key}'
    created_at  REAL NOT NULL
);

-- ② 参数选择状态机（落 DB，重启不丢）
CREATE TABLE IF NOT EXISTS feishu_pending (
    channel     TEXT NOT NULL,           -- 'feishu'
    chat_id     TEXT NOT NULL,
    sender_id   TEXT NOT NULL,           -- open_id
    kind        TEXT NOT NULL,           -- 'draw_params' | 'edit_intent' | 'edit_prompt'
    payload     TEXT,                    -- JSON：草稿参数
    created_at  REAL NOT NULL,
    expires_at  REAL NOT NULL,
    PRIMARY KEY (channel, chat_id, sender_id, kind)
);

-- ③ 任务跟踪 + 看板消息 id（用于"编辑同一条"而不是刷屏）
CREATE TABLE IF NOT EXISTS feishu_tracks (
    job_id      TEXT PRIMARY KEY,
    channel     TEXT NOT NULL,
    chat_id     TEXT NOT NULL,
    sender_id   TEXT NOT NULL,
    is_group    INTEGER NOT NULL DEFAULT 0,
    board_msg_id TEXT,                   -- 看板消息 id（edit 用）
    phase       TEXT,                    -- queued|generating|uploading|done|failed|waiting
    notified    TEXT,                    -- JSON：已发过的节点，防重复通知
    created_at  REAL NOT NULL,
    updated_at  REAL NOT NULL
);
```

要点：
- **不改 `jobs` 表**（A 链既有契约，网页/商户中心都依赖它）；机器人只做**外挂跟踪表**
- `feishu_tracks` 是**崩溃恢复的依据**：重启后 `SELECT * FROM feishu_tracks WHERE phase NOT IN ('done','failed')` → 重建轮询
- 所有表放**同一个 SQLite**（`flux_db` 那套），复用 WAL 与连接管理

## 5. 身份与额度

| 概念 | 设计 |
|---|---|
| 飞书用户身份 | `open_id` **直接当 A 链的 user_id**（现有代码已这么做：`db.user_ensure(open_id)`） |
| owner | `FEISHU_OWNER_OPEN_ID` → `db.set_owner()`，**无限量**（已实现，保留） |
| 普通用户 | 第一期：各自独立账户（飞书额度与网页额度**分开**） |
| 绑定（第二期） | `/bind <激活码>` → 复用 `/api/activate`：把 open_id 与已有账户关联，**共享同一份额度** |
| 消耗口径 | 群里消耗**发起人**的额度，回执里明示"本次消耗 1 张，剩余 Y" |
| 未激活用户 | 发提示词 → 回「请先发激活码（`/bind XXXXXXXX`）」；**不允许白嫖** |

> ⚠️ **必须明确写下来的取舍**：飞书身份与网页 token 是两套 ID。
> 不绑定时，同一个人会有两份额度 —— 这是**有意为之**（第一期求快），不是 bug。
> 第二期用 `/bind` 收敛。

## 6. 分阶段落地（每阶段都有验收标准）

| 阶段 | 内容 | 输入 | 输出 | 验收标准（可机器判定） |
|---|---|---|---|---|
| **P0**<br>半天 | 修 3 个缺陷 | 现有 `feishu_bot.py` | ①`MAX_ACTIVE` 超出**必须回执**<br>②加去重（`evt:` + `filekey:` 双键）<br>③在途任务落 DB + 重启恢复 | ①同一 event 重放 2 次**只出 1 张图**<br>②第 51 个任务收到明确回执<br>③提交后重启 9620，任务完成后**仍收到图** |

### 建议的开发顺序为什么是这样

P0 先做，因为**它修的是"会烧钱 + 会丢用户结果"的缺陷**（重复出图扣额度、重启丢结果、静默不跟踪），
这些不修，后面的功能越多亏得越多。P1/P2 是"体验对齐小白"的主体。P3 是能力扩展。P4/P5 是打磨与风控。

## 8. 决策记录（2026-09-23 用户已拍板）

| # | 决策项 | 结论 | 落地影响 |
|---|---|---|---|
| 1 | **机器人宿主** | **选 A：保持现状（A 链进程内，随 9620 启停）** | 零新增部署，今天就能用；代价 = **本机关机/休眠时图图不响应**。为保留后路，渠道层/编排层仍按 §2.1 写成**只依赖 HTTP 的纯 Python**，将来迁 VPS（方案 B）只是换宿主，不重写 |
| 2 | **额度模型** | **先做激活码绑定**：`/bind <激活码>` 复用 `/api/activate` 语义 | 飞书 `open_id` 与已有账户**共享同一份额度**，不做两套账；未绑定用户发提示词 → 回「请先发激活码」 |
| 3 | **服务范围** | **只服务 owner 自己 + owner 自己的群** | 群白名单；非白名单群/用户一律不响应；owner 无限量（现有 `set_owner` 保留） |

**对分阶段计划的三处调整**：
- 决策 2 把「`/bind` 激活码绑定」**从 P5 提到 P1**（一期就要绑定），P5 只保留速率限制与群配额
- 决策 3 把**群白名单**从可选变成 **P2 的前置条件**
- 决策 1 让 **P6（迁 VPS）暂缓**，但代码必须保持可迁移

### 以下为原始选项说明（保留作决策依据）

### 决策 1：机器人宿主放哪？（影响最大）

### 决策 1：机器人宿主放哪？（影响最大）

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 保持现状（A 链进程内）** | 图图随 9620 跑在你本机 | **零新增部署**、能直接调 `scheduler`（无网络跳、无鉴权问题）、今天就能用 | **本机关机/休眠 = 机器人哑**；本机没开网就收不到 |
| **B. 迁到 VPS（像小白那样）** | 独立 `flux-bot.service`，通过 HTTP 调 A 链 | **7×24 在线**，效果真正对齐小白 | 要新增部署单元、要处理调用鉴权（admin token 或新建 bot token）、要在 `sync-from-main.sh` **登记新文件**、要防止与 9620 排队状态不一致 |

**我的建议**：**先 A 后 B**。理由：第一期把「渠道层 + 编排层」写成**纯 Python 模块、只依赖 HTTP 而不是进程内对象**，
这样 P6 迁 VPS 就只是"换个宿主"，而不是重写 —— 这是唯一的低成本迁移路径。

### 决策 2：额度模型

- **第一期：飞书身份独立额度**（快，代价 = 同一个人两份额度）
- 还是**一期就做绑定**（`/bind 激活码`，让飞书身份与网页账户共享额度）？

### 决策 3：群聊范围

- 只服务你自己的群（白名单群 id）
- 还是对外（任何把你拉进群的人都能用）→ 那就必须一期就上**每人日限额 + 激活码门槛**

## 10. 一句话总结

**"图图"已经有了，缺的是"完整"**：它现在是「私聊直出脚本」，要变成「和小白同级的对话式出图助手」，
需要补的是 **去重 / 状态机 / 群聊 / 图生图 / 看板 / 可恢复** 这六件事，
而**分层结构与全部踩坑经验都已经在小白那边验证过**，可以直接搬。
最大的一次性决策是**机器人宿主**（本机 vs VPS），它决定"本机关机时图图是否还活着"。
