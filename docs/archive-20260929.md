## 一、本次归档包含什么

本轮的实质工作 = **多图参考（「模特穿搭」）全链路打通**。

需求原话：「把多个产品的图穿到一个模特图上」。

这是一个**跨仓特性**：站点侧要能多选图 + 标角色 + 切「穿搭」意图，
上游侧要能接受 `images[]`、按张数选机、持久化张数、并在选机时避开只支持单图的机器。
因此本次**两仓同批归档**（这是本项目首次两仓一起归档 —— 上一份 flux 归档里
image-gen-site 只是标注了 HEAD，没有配对归档）。

需求脉络（用户连续指令）：「把多个产品的图穿到一个模特图上」→（中途排查 3 处门假红）
→「现在实现 + 离线验证，真机验证等有卡」→「做个归档」。

### ★ 本轮最关键的两处（都不是"加功能"，是修理解偏差）

**① 中间层把能力字段丢了（根因修复）**
站点一直拿不到 `supports_edit`，注释以为是"上游版本旧"，实际是
`_api_models` 的 `slim` 只留 5 字段、把 GPU 侧明明给了的 `capabilities` **过滤掉了**。
穿搭要靠 `capabilities.multi_ref` 判多图，拿不到就只能猜模型名 —— 修法：补回字段，
缺失给 `None`（「不知道」≠「不支持」），`path` 仍不外传。

**② 「门红的是它自己」（3 处，产品代码 0 缺陷）**
本次归档前，e2e 一度 17/3 红，逐项查后确认**全是测试/环境侧**：

| 假红项 | 真因 |
|---|---|
| T8b / T8c（模型按钮） | 门在**追**异步 `/api/models` 的返回值，机器慢就必红 → 改成轮询等待（≤20s） |
| `timeout: Runtime.evaluate` | 门把 CDP 超时**硬编码 60s**，短于页面自身 150s 循环 → 吞掉真正的失败原因（403） |
| `run_all` 里 1 道红 | WorkBuddy 注入的 **Python 级删除钩子**（非 shell 别名）拦批量删除 → 单跑绿、合跑红 |
