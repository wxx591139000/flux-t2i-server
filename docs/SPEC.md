# 项目目标 SPEC — FLUX 文生图服务（通用）

> 版本：v2.0 · 2026-09-04

## 项目定位与目标

搭建一套**自部署 FLUX.1 文生图服务**，作为通用能力平台，**与具体业务解耦**，可服务所有文生图需求（小红书配图、公众号配图、海报底图、素材生成等）。

**核心目标**：
1. 服务器端能批量文生图（读提示词文件逐张生成）
2. 本地端能自动检测服务器开机+带卡 → 一键启动生成（对标转录 bot 的开机自启机制）
3. 无卡模式下也能完成模型下载（curl 流式绕开 huggingface_hub 失败问题）
4. 一键操作、幂等安全、断 SSH 可后台跑
5. **对外文生图服务（v1.1）**：Web 提交提示词 + 排队调度 + 配额计费 + 公网隧道（对标转录bot）
6. **飞书"图图"对话式出图（v1.7）**：飞书私聊发提示词 → 接入队列生成 → 图片回传飞书对话（借鉴转录bot"小白" WS 范式）
7. **多服务器（v2.0）**：任务中心 `FLUX_SERVERS` 注册表管理多台 FLUX 机，每单自动挑任一台「可达+带卡+模型就绪」的服务器执行——任一台开机即可接单（单 worker 串行，用户确认并发策略）
8. **VPS 看门狗（v2.0）**：常开 VPS systemd 长驻巡检各 FLUX 机，机器在线但未就绪 → 自动就地预热成可接单（预热就绪+保活，真正生图仍由任务中心按需调度）

## 技术栈与架构概览

- **推理**：diffusers `FluxPipeline`（不用 ComfyUI，服务器 github 被墙）
- **模型**：`black-forest-labs/FLUX.1-dev`（gated，分片权重 ~31GB）
- **环境**：conda env `flux`（python3.12 / torch 2.13+cu130 / diffusers 0.39）
- **服务器**：AutoDL VGPU 32G（无卡/带卡两种模式）
- **下载**：curl + hf-mirror 镜像 + token 鉴权
- **后台**：screen（可断 SSH）
- **对外服务**：stdlib `http.server`（无框架）+ SQLite + PriorityQueue + cloudflared 隧道 (v1.1)

### 飞书出图（v1.7）
- 入口：飞书私聊"图图"机器人，直接发文本提示词（支持中文自动翻译）
- 用户身份：飞书 open_id 即 user_id（首次自动建用户），owner（`FEISHU_OWNER_OPEN_ID`）无限量
- 交互：确认回执（任务号+用量）→ 服务器down通知 → 完成回传图片 / 失败回错误
- 约束：仅 P2P 私聊；每用户最多 1 个在途；斜杠开头给提示语（暂不支持命令）
- 依赖：`lark-oapi`（WS 长连接监听）

## 已知约束与边界

- **需要带卡模式才能生成**（无卡无 GPU）；无卡仅能下载模型
- **模型是 gated 仓库**，需 HF token（从环境变量 `HF_TOKEN` 读，不硬编码）
- **服务器被墙**：huggingface.co / github 不可达，需 hf-mirror + aliyun pip 镜像
- **分片大小必须用 HF API 真实 LFS 字节数**，不能猜（猜小会损坏文件）
- 生成 768×1024（3:4）约需数秒~数十秒/张，CPU offload 下速度偏慢
- **GPU 单卡严格串行**：队列 worker 单线程，多用户需排队（~85s/张）(v1.1)
- **配额入队即扣**：每月图片数按 token 计，owner 无限 (v1.1)
- **密钥/凭证绝不入库**：`.env`、token、日志、运行时 data 均在 `.gitignore` (v1.1)

## 增量（2026-09-24）：图图命令面 + 取消任务（v2.10.0）

**新增能力**：飞书「图图」支持**取消在途任务**（此前只能提交，不能撤回）。

| 命令 | 行为 |
|---|---|
| `帮助` / `help` / `/help` | 命令清单 |
| `我的任务` / `我的排队` / 裸 `取消` | 列出在途任务（编号 + 提示词 + 状态 + 短号） |
| `取消 01` / `取消01` / `取消任务 01` | 按列表序号取消 |
| `取消 <6~16 位 hex>` | 按 job_id 前缀取消（序号漂移时的退路） |

**两条硬性语义**（进 SPEC 是因为它们约束了输入通道的设计）：

1. **命令识别必须早于提示词提交**。图图的命令与提示词**共用同一条输入通道**
   （飞书文本消息），所以判定顺序错了会把命令当提示词提交
   → **真的扣一次额度并出一张毫不相干的图**（用户想撤回反而多花一次）。
2. **命令判据必须严格**：只有「取消 + 序号/短码」才算命令，
   否则会吞掉以"取消"开头的正常提示词（如「取消一切杂乱背景，画面干净」）。
   斜杠写法（`/取消 01`）也接受。

**取消的语义**（复用既有 `/api/delete`，不新造一套）：

| 原状态 | 取消后 |
|---|---|
| `queued` | 从待跑队列剔除，**不烧 GPU** |
| `generating` | **撤不回来**（GPU 已在跑）；打墓碑 → worker 跑完**丢弃产物** |
| `waiting` | 从等待恢复池剔除，机器上线后**不会再跑它** |
| 终态 | 本就不在列表里 |

**配额口径**：**取消不退还额度**（与网页端 `/api/delete` 一致；用完即消耗，防"删了重传"）。
所有取消回执都明写这一条。

## 增量（2026-09-28）：参数状态机 + 绑定 + 群聊（v2.11.0）

### 参数状态机（会话默认值）

| 命令 | 行为 |
|---|---|
| `比例 16:9` / `/size 16:9` | 设等比（`1:1 / 16:9 / 9:16 / 4:3 / 3:4` → 宽×高） |
| `张数 3` / `/n 3` | 设张数（上限 4） |
| `模型 klein` / `/model dev` | 设模型（别名 `klein/dev/qwen`，也接受完整 model id） |
| `参数` / `/params` | 查当前会话默认参数 |
| `额度` / `/quota` | 查套餐与额度 |
| `绑定 XXXXXXXX` / `/bind XXXXXXXX` | 激活码绑定；与网页账户**共享同一份额度** |

**会话身份 = 三元组 `(channel, chat_id, sender_id)`**（不是二元组）。

> 为什么是三元组：二元组 `(channel, sender_id)` 把"同一个人在群里的会话"和
> "他的私聊会话"**当成同一个** → 群里设的「张数 3」会串到私聊。
> 三元组把隔离做在**数据层**（`feishu_prefs` / `feishu_pending` 两张表的主键就含 `chat_id`），
> 跨会话误消费**结构上不可能发生** —— 不靠调用方记得加守卫。

**待选状态机**：选项认不出时不再静默丢弃，落 `feishu_pending`（主键含 `kind`，TTL 300s），
下一条消息先试消费待选、再当提示词。**消费顺序**：命令 → 待选 → 提示词（见下）。

### 命令识别顺序（硬要求，与 v2.10.0 同源，本版扩了面）

```
① 判命令（严格判据；命中则**先清待选**，避免「取消」被当成"选第 N 项"）
② 试消费待选（`_try_consume_pending`）
③ 都不是 → 当提示词提交
```

判据只认**命令词/前缀 + 参数**，且**拉丁字母的裸词不算命令**（除斜杠写法）——
避免把英文提示词误吞。命令词表见 `manager/figu_state.py`。

### 多图语义：一次翻译、多张候选

`张数 n > 1`：第 1 张正常提交（翻译由调度器做），随后**从 `jobs` 表读回第 1 张实际落地的
英文提示词**作为第 2..n 张的输入，并**显式给不同 seed**（去重键含 seed）。

> 为什么不各自翻译：翻译会漂移 → n 张图不是"同一句话的候选"而是 n 张不相干的图；
> 且 n×LLM（最坏 68s）全压在工作线程上，会拖住其他用户。
> 为什么从库里读回而不是自己再翻：**不复制 `submit()` 的翻译策略**（复制必然漂移）。

### 群聊（两道门）

| 门 | 规则 |
|---|---|
| 白名单 | `FEISHU_ALLOWED_CHATS`（逗号/分号分隔）。**默认空 = 一个群都不服务** |
| @门 | 必须 @图图**本人**：`message.mentions[].id.open_id == FEISHU_BOT_OPEN_ID`，**不是**文本里的 `@` |

**回程路由**：群消息的回复与结果**回到原群**、只 @ 发起人；私聊不变。
跟踪行记 `chat_id` / `is_group` → 9620 重启后仍能回对地方。

**未配 `FEISHU_BOT_OPEN_ID` 的降级行为**：@ 判定退化为"任意 @ 即响应"并打 WARNING ——
白名单群内可接受，但**不算正确**（会误响应 @别人 的消息）。

### 顺带收敛的判据（`cancelled` 终态）

在途/终态判据统一引用**单一事实源** `FEISHU_TERMINAL_PHASES = ('done','failed','cancelled')`。
此前两处漏了 `cancelled` → 取消过的任务**仍算在途**（配合 `MAX_INFLIGHT_PER_USER=1` =
取消一次就再也提交不了），且 GC 永不清理该行。

## 增量（2026-09-28）：图图提交前确认（v2.12.0）

**需求（用户原话）**：「给图图发消息时并不都是生图的提示词，建生图任务前要在对话里
进行确认是否发送"XXXX"生图任务」。

非命令文本**不再直接提交**：

```
用户: 一只橘猫坐在窗台上
图图: 🤔 要把这一句作为生图任务提交吗？
      「一只橘猫坐在窗台上」

      本次参数：1 张 · 比例 默认 · 模型 默认
      回「是」开始出图 / 回「否」放弃
      （5 分钟内有效；不回也没关系，不会扣额度）
用户: 是
图图: ✅ 收到！正在排队生成「一只橘猫坐在窗台上」…
```

| 用户输入 | 行为 | 额度 |
|---|---|---|
| 「是」「好的」「ok」「确认」「提交」「出图」 | 建任务并排队 | 消耗 |
| 「否」「算了」「不用」「放弃」 | 放弃 | **不消耗** |
| 别的文本（含直接发下一句提示词） | 旧确认作废 → 按新提示词**重新确认** | 不消耗 |
| 什么都不回（5 分钟后过期） | 作废 | **不消耗** |

**判据三条**：
1. 确认词**只认全等**（`figu_state.parse_confirm`）—— `好` 是确认，`好可爱的一只猫` 不是；
2. 参数走**快照** —— 确认消息里显示的参数就是提交用的参数（`prefs_override` **整体替换**），
   杜绝「确认时说 2 张、实际出 3 张」；
3. 未知回复**不消费**（返回 False）—— 让新提示词照常走确认流程，不被吃掉。

**顺序（硬要求）**：命令 → 待选 → 未知斜杠 → **确认** → 提交。

**开关**：`FIGU_CONFIRM_SUBMIT`，默认**开**；设 `0` 回退旧行为（应急）。
⚠️ 显式留空按「未设」处理 = 开。

## 增量（2026-09-28）：模型许可闸与业主放行（v2.13.0）

> ⚠️ 本节补的是一处**文档缺口**：许可闸自 2026-09-22 起就是运行时硬约束，
> 却从未写进 SPEC/ARCHITECTURE，只存在于代码注释与测试里。现在补上。

### 约束（法律，不是质量偏好）

对外**自动选机**不得把任务派给「许可不允许商用」的模型。B 链是面向客户的生图服务，
用非商用模型接单不是"效果差一点"，是**违反许可**。

### 两个正交字段（注册表 `manager/servers.json`）

| 字段 | 回答的问题 | 性质 | 谁能改 |
|---|---|---|---|
| `commercial_ok` | 许可证允不允许商用？ | 客观**事实** | 谁都不该改（除非上游改许可） |
| `license` | 许可名（人类可读，便于评审） | 事实的**依据** | 同上 |
| `expose_to_customers` | 业主愿不愿意承担、放给客户？ | 主观**决定** | 业主 |
| `expose_note` | 这个决定的依据（谁/何时/为什么） | 决定的**留证** | 业主 |

★ **为什么不合并成一个字段**：改成 `commercial_ok: true` 等于让事实字段撒谎，
后来者再也分不清「模型本来就允许商用」与「业主决定不管许可」—— 而这两件事的法律含义完全不同。
所以：事实字段不动，另加一个决定字段。

### 判据（`flux_resident_client._pick_from`，位于**能力过滤之前**）

```python
allowed = [c for c in cands
           if c[0].get('commercial_ok') is not False      # ① 许可事实允许
           or c[0].get('expose_to_customers') is True]    # ② 业主显式放行
```

| 取值 | 结果 |
|---|---|
| `commercial_ok=True` | 放行 |
| `commercial_ok` **缺字段** | 放行（**向后兼容**：老部署没这字段，剔除会让全部机器消失） |
| `commercial_ok=False` 且无 `expose_to_customers` | **拦下** |
| `commercial_ok=False` 且 `expose_to_customers=True` | 放行（+ `WARNING`，每台每进程一次） |
| 全部候选都被拦 | 返回 `None`，**不硬挑**（交给调用方报准确原因，避免「提交成功→排队→报错」白等一轮） |

**两个既有豁免不变**：
- `need_model` —— 用户**显式点名**要哪个模型时绕过闸（自用指定 Qwen 必须可行，许可由他自己负责）；
- `DIRECT_BASE` —— 直连模式下候选机只是"连接参数载体"，带着注册表首台的标签，跳过闸
  （否则本地部署 / 离线测试会把唯一那台"机器"误判成非商用 → 全部任务返回"无可用机器"）。

### 可见性

靠 ② 放行的机器被选中时打 `logger.warning`（按机器名去重，每进程一次）——
这是个**法律风险开关**，最糟的形态是「悄悄生效」；但每轮刷屏同样是伤害
（本项目看门狗专门为刷屏做过节流，因为刷屏会淹掉真正的故障日志）。

`tests/test_commercial_gate.py`（17 项）+ `tests/test_model_capabilities.py` 的 `t_license`：
