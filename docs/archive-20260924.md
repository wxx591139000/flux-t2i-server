## 一、本次归档包含什么

本轮的实质工作 = **图图「取消任务」（P1 第一块）** + **一个真缺陷的修复**。

需求原话：「像小白一样有取消任务的能力吗」。

**结论：底层早就有了** —— 2026-09-21 为网页端写的 `/api/delete` + `queue.drop_job()` +
`deleted_at` 墓碑机制，语义恰好就是"取消"（连 generating 的"撤不回来但丢弃产物"都实现了）。
缺的只是**图图这一层的命令面**。所以本轮不是新造一套，是**把图图接到既有能力上**。

## 二、变更摘要

### 新增：图图命令面（中文裸命令，对齐小白）

| 命令 | 行为 |
|---|---|
| `帮助` / `help` / `/help` | 命令清单 |
| `我的任务` / `我的排队` / 裸 `取消` | 列出在途任务 |
| `取消 01` / `取消01` / `取消任务 01` | 按列表序号取消 |
| `取消 <6~16 位 hex>` | 按 job_id 前缀取消 |

两个硬要求（都有门钉住）：
1. **命令识别早于提示词提交** —— 否则「取消 01」被当提示词**真扣额度出废图**
2. **不吞掉以"取消"开头的正常提示词** —— 判据严格到"取消 + 序号/短码"

### ★ 修掉的真缺陷：已删的 `waiting` 任务「复活」并**拿到退款**

- `/api/delete` 的 `inflight` 判据**不含 `waiting`** → 删除 waiting 时不调 `drop_job`
  → 调度器内存等待池留幽灵项
- `_recover_waiting_tasks()` 从内存池 pop 后**直接重新入队，原先没有墓碑检查**
- 后果：`waited > 4 小时` 那条分支会给**已被用户删除的任务退款**
  → 正是 `job_mark_deleted` 明确要防的「删了重传无限刷额度」

**修法（三道闸）**：拆 `inflight`/`pooled` 判据 + 恢复入口独立墓碑过滤 + worker 原有检查。

**变异实证**（摘掉过滤后）：`实际退款 [('sAlive','等待服务器超时(250分钟)'), ('sDead','等待服务器超时(250分钟)')]`

### 另修：跨渠道取消

网页端删任务后，飞书 `feishu_tracks` 表不知道 → 轮询永远盯着它（**永不收敛**）。
→ `_poll_once` 加墓碑优先分支；`feishu_tracks_pending()` 终态集合补 `'cancelled'`。
